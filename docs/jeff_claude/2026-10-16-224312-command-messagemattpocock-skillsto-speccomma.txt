⏺ Escrito para: el equipo y los agentes que van a implementar el backend
  (español, identificadores en inglés, como el spec del proxy).

  Dejé el spec en docs/issues/backend-relia-api.md, con la etiqueta
  ready-for-agent. No lo subí a GitHub porque gh no tiene sesión; queda local
  como el spec del proxy. No escribí código ni toqué db_ddl.sql; eso queda para
  los tickets.

  Lo que define el spec:
  - Base local: docker compose up levanta postgres:16 y aplica db_ddl.sql la
    primera vez que se crea el volumen. Como elegiste, db_ddl.sql es el único
    DDL. Hay que ajustarlo para que corra fuera de Azure (sobra AUTHORIZATION
    azure_pg_admin y los triggers aparecen antes que sus funciones) y agregarle
    lo que el contrato necesita:
    - una tabla para guardar las Idempotency-Key;
    - operations.failure_code y operations.cash_handed_over_at;
    - agents.wallet_simulated;
    - payments.rail_payment_id y payments.rail_version.
  - Siembra: vive en el backend y es la misma para el primer arranque y para
    POST /demo/reset.
  - Verificación: manual con la colección de Postman, contra el backend, la base
    en Docker y el proxy real. Al final de cada flujo, la vista
    v_agent_balance_check tiene que dar los descuadres en 0. No hay proyecto de
    pruebas.

  Lo que encontré y cambia el trabajo:
  - El mapeo de EF apunta al esquema viejo. El código actual usa los nombres del
    esquema v0.2 en español (corresponsales, cupos…) y db_ddl.sql está en
    inglés (agents, agent_balances…). Hay que reescribir el mapeo antes de
    cualquier otra cosa. Los servicios siguen todos en stub (responden 501).
  - La base impone un orden al completar una operación. Primero el pago pasa a
    completed, después la operación (ahí se congela el recibo) y por último el
    movimiento. Los triggers rechazan cualquier otro orden.
  - En un depósito, el cupo baja el monto cobrado (neto + tarifa), no el neto.
    Así lo valida la base, así que el desglose y las reservas tienen que usar la
    misma regla.
  - La carga Bre-B y la liquidación con billetera simulada necesitan una fila en
    payments, porque la base exige un pago completado para cada movimiento. En
    el spec quedan como pagos con riel bre_b_simulated.

  Pendiente:
  - El spec anterior y sus tickets. Este reemplaza a
    01-implementar-backend-relia-api.md
    (docs/wayfinder/relia-api/issues/01-implementar-backend-relia-api.md). Ese
    spec y sus tickets 02–17 asumen el esquema en español y Testcontainers, y no
    los marqué como reemplazados. Lo que sigue es cortar tickets nuevos con
    /to-issues; el spec ya trae el orden sugerido.
  - El .env del proxy no está ignorado. Hay un rail-proxy/.env en el repo y el
    .gitignore de rail-proxy/ no lo excluye. Conviene revisar que no tenga la
    llave privada de Relia antes de hacer push.

› Message from general-purpose
  **(a) Missing or partial**

  1. **Ledger does not calculate reservations.** Spec: "Ledger de saldos: …
  Calcula las reservas a partir de las operaciones pendientes". `ILedger` only

  repeat that logic.
  2. **Ledger is not yet the only writer.** Spec: "único lugar que cambia
  `agent_balances` y escribe `ledger_entries`". The ticket notes say the seed
  still writes balances directly. The gap is acknowledged but not ticketed.
  3. **Postman checkbox is open.** "[ ] Verificado con la carpeta
  `cash-adjustments`". The status is correctly ready-for-human.

  **(b) Scope creep (minor)**

  - `Program.cs` changes `errors[].field` for keys containing a hyphen, which
  affects every endpoint, not just this one.
  - `resource_id` stores the full `Location` URL. Spec: "id del recurso". For
  this route it is always null anyway, because the controller returns
  `StatusCode(201, …)` with no `Location`.
  - Ticket 03 doesn't ask for `EnsureCanOperateAgent`, but it serves US 103
  ("admin recibe 403 … al crear … ajustes"), so this is fine.

  **(c) Looks implemented but wrong**

  1. **The adjustment can apply twice.** Spec: "repetir el ajuste con la misma
  `Idempotency-Key` no sume dos veces" (US 33). In `IdempotencyFilter.cs`, the
  record is saved in a separate `SaveChangesAsync(ct)` after the service's
  transaction has committed, and `ct = http.RequestAborted`. If the client
  disconnects or times out after the commit, the save is cancelled and no record
  exists. The client's retry, the exact case idempotency exists for, then
  applies the adjustment again. The record should be written in the same
  transaction as the ledger entry, or at least not use `RequestAborted`.
  2. **Missing `mode` or `amount` are not rejected.** Contract:
  `CreateCashAdjustmentRequest required: [mode, amount]`. `Dtos.cs:89-92` uses a
  non-nullable `long Amount` and `CashAdjustmentMode Mode`, and `[Required]`
  does nothing on value types. No strict JSON option is set in `Program.cs`. A
  body of `{"mode":"set"}` sets cash to 0 and returns 201. A body of
  `{"amount":5000}` silently runs as `add`. The DTO predates this diff, but this
  ticket's rules depend on it.
  3. **Scope depends on the URL's exact text.** Spec: "alcance (ruta + actor)".

› Message from general-purpose
  **Correctness and concurrency (most important first)**

  1. **IdempotencyFilter.cs:79-94. Hard bug.** The idempotency record is saved
  after the service has already committed its transaction (`InTransactionAsync`
  commits at EfRepositories.cs:17), and that save uses `ct = RequestAborted`. If
  the client disconnects or the process crashes between the commit and line 94,
  the adjustment stays applied but no record is written. The client's retry
  with the same key then applies it a second time. Fix: write the record inside
  the same transaction, or at minimum pass `CancellationToken.None` to that
  save.
  2. **IdempotencyFilter.cs:45. Scope uses `Request.Path`.** The raw path is
  case-sensitive and keeps trailing slashes, so `/agents/ABC…` and
  `/agents/abc…` produce different scopes. The same key on both would run twice.
  Build the scope from the route template plus route values.
  3. **IdempotencyFilter.cs:99-105. Lock release.** If `pg_advisory_unlock`
  throws (for example on a broken connection), that error replaces the original
  exception. The lock itself is probably safe: by default Npgsql resets a pooled
  connection when it is reused, which frees advisory locks. The release also
  relies on the connection opened at :51 being the one the service's transaction
  later uses. It is today, because the DbContext is shared, but nothing in the
  code states or checks that.
  4. **IdempotencyFilter.cs:87-92. Speculative branch.**
  `CreatedResult`/`AcceptedResult` never match, because the controller returns
  `StatusCode(201, …)`, an `ObjectResult`. `ResourceId` is therefore always
  null. `CreatedAtActionResult` would not match either.
  5. **EfRepositories.cs:30-38.** Locking with `FOR UPDATE` and then calling
  `ReloadAsync` gives correct values: the lock is already held, so the second
  SELECT reads the latest committed row. The costs are one extra round-trip and
  that `Reload` silently throws away any unsaved tracked changes to that
  balance. Worth a comment.
  6. **CashAdjustmentService.cs:34.** In `set` mode, a negative amount is
  already rejected by `[Range(0,…)]` on the request, so that is fine.
