  **Standards review: uncommitted backend diff (GET /agents admin panel)**

  **Hard violations of documented standards: none.**
  - Contract (`contracts/relia-api.openapi.yaml`,
  `AgentSummary`/`NetworkTotals`/`CountAmount`/`AgentList`): the DTO records in
  `Contracts/Dtos.cs` match field-for-field, including the `admin` tag and 403.
  - Spec rule "servicio + repositorio + IUnitOfWork"
  (`docs/issues/backend-relia-api.md`): followed.
  - Role rule: `EnsureAdmin` sits in `CurrentUserAccess` and the service uses
  it. Putting `[Authorize(Roles=...)]` on the controller as well matches the
  existing pattern, as does the raw-SQL row record (like `HistoryRow` in
  `Repositories/Abstractions.cs`) and Spanish comments.

  **Judgement calls (baseline smells):**

  1. **Mysterious Name / naming drift** (`Repositories/Abstractions.cs`
  `AgentSummaryRow` vs `Services/AgentService.cs`):
     - The row has `CommissionPayable` and `CommissionPaidTotal`, but the DTO
  maps them into `AccruedCommission` and `SettledCommissionTotal`.
     - Totals then use `items.Sum(a => a.AccruedCommission)` for
  `CommissionPayable`.
     - The same concept has two names on each side. Naming the row's properties
  after the DTO (it's an alias in the SQL anyway) removes the translation.

  2. **Data Clumps / long positional constructor**
  (`AgentService.ListAgentsAsync`):
     `new AgentSummaryDto(r.AgentId, ..., r.TotalMoved, r.Quota, r.CashOnHand,
  r.CommissionPayable, r.CommissionPaidTotal, r.CommissionPaidToday)`
     This passes 15 positional args, and 6 of them are adjacent `long`s, so a
  swap would compile silently. Named arguments would make the order safe; no new
  type is needed.

  3. **Duplicated Code / logic split** (`AgentService`):
     `new CountAmountDto(deposits.Count + withdrawals.Count, deposits.Amount +
  withdrawals.Amount)`
     The service rebuilds "total moved" as deposits + withdrawals, while the
  view already exposes `total_moved` per agent (read as `r.TotalMoved`). The
  definition of "moved" now lives in two places, the view and C#. Summing
  `TotalMoved` for the amount would remove that. There is no `total_moved` count
  column, so the count would still be computed in C#.

  4. **Feature Envy (minor)**: the row-to-DTO mapping and the totals aggregation
  both live in `AgentService`, so the service mostly reshapes repository data.
  This is acceptable for the size; a static `ToDto` next to the row is optional.

  5. **Comment** (`AgentsController`): the comment `// "~/" no combina con la
  ruta del controlador` is fine. Making `/agents` the only route that escapes
  the class-level `[Route("agents/{agentId:guid}")]` is a mild structural
  oddity, but it's documented.

  **Housekeeping (not in the diff, but in the working tree):** there's an
  untracked file, `backend/API/Domain/Entities.cs.new`. It differs from
  `Entities.cs` only by a removed `<summary>` comment line and a trailing line.
  It looks like a leftover and shouldn't be committed.

  1. **IDs change after reset.** The spec doesn't address this. Spec: "vuelve a
  correr la siembra del ticket 01". `DemoSeeder.cs:104,109,117` uses

  at an admin or agent that no longer exists, and the demo script needs a fresh
  login mid-presentation. I did not check whether endpoints answer such tokens
  with a clean 401/404 or with a 500. Fixed seed GUIDs would fix this cheaply;
  the implementation notes already suggest it.
  2. **Reset continues when the rail fails.** Spec: "cancela en el riel los
  cobros pendientes". `DemoService.ResetAsync` catches `RailException`, logs it
  and carries on. This is defensible, but two side effects are worth knowing:
     - With the rail down, each pending charge waits out the full HTTP timeout
  one after another, so the reset can hang for a long time.
     - A charge left alive in the rail can still be approved later and move real
  money with no operation behind it.

     The cancellations also run before the TRUNCATE transaction, so a charge
  created between the listing and the TRUNCATE is not cancelled. Low risk in a
  demo.
  3. **Expire 409/503 semantics.** Spec: "Si no está pendiente responde `409`, y
  si el riel no responde, `503`." This is correct: a deposit or non-pending
