⏺ Escrito para: el equipo de Relia que va a probar la API y el proxy en Postman.

  Creé contracts/README.md. Esto no necesitaba pasar por ningún flujo de skills
  (grill, spec, tickets), así que escribí el archivo directamente.

  Qué explica:
  - Relación entre archivos: el YAML de OpenAPI es la fuente de verdad y las
    colecciones se generan a partir de él. Incluye una tabla con URL local y
    tipo de autenticación de cada servicio (Bearer en la API, X-Api-Key en el
    proxy).
  - Primeros pasos: importar las colecciones y crear un environment con
    bearerToken y apiKey. Las colecciones solo traen baseUrl, así que sin esas
    dos variables todo responde 401.
  - Login automático: un script post-response para el login que guarda
    bearerToken y agentId solo.
  - Datos de ejemplo: cuáles hay que reemplazar antes de enviar (<uuid>, payment
    pointers inventados como $=*rh5j, montos en unidades mínimas) y el truco
    {{$guid}} para Idempotency-Key.
  - Convenciones del contrato: idempotencia, consultas periódicas (polling) en
    lugar de webhooks, formato del dinero y errores en problem+json.
  - Flujos de prueba: una secuencia sugerida para la API y otra para el proxy.
  - Cómo regenerar las colecciones con los comandos exactos.

  Comprobaciones:
  - Ejecuté openapi-to-postmanv2@6.4.0 sobre rail-proxy.openapi.yaml y genera
    las mismas carpetas, la misma autenticación y el mismo baseUrl que la
    colección que tienen guardada. No lo corrí sobre relia-api.openapi.yaml.
  - Revisé contra los YAML los estados de pago, el formato del payment pointer y
    idempotency_conflict.

  Dos cosas a tener en cuenta:
  - En la colección del proxy, todos los ejemplos de error muestran code:
    same_wallet. Es un fallo del generador, no del contrato, y lo dejé anotado
    en el README.
  - El script de login se pierde cada vez que se reimporta una colección
    regenerada. Si eso molesta, se puede meter en el pipeline de generación.
